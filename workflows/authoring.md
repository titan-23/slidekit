# 資料を作成する手順

この手順は、AI または人が `slidekit` を使って資料を作成する際の作業規則である。
ライブラリ自身が AI を呼び出したり、修正回数を制御したりするものではない。
コマンドと引数の詳細は [利用ガイド](../docs/usage.md) にある。

## 入力を確認する

1. 利用者の依頼を読み、対象者、発表時間、必須事項を確定する。資料に `brief.md` があれば併せて読む。
2. 新しく作る資料は直下に完成物と README、`src/` に編集元と作業用のファイルを置く構成にする（[ディレクトリの構成](../docs/usage.md#ディレクトリの構成)）。既存の資料は今の構成のまま作業する。
3. `deck.toml` の元資料、書誌情報、素材、参照範囲、完成物の保存先を確認する。
4. 資料側で指定された記述規則を読む。
5. 題名、著者、最終更新者を指定する。匿名の場合は意図して空欄とする。

元資料の取り扱いは依頼の条件にしたがう。変換はローカルで行う。
資料の Python コードに、外部通信や無関係なファイルの変更を含めない。
これは作業上の規則であり、Python の実行を技術的に隔離する保証ではない。

## 編集元を書く

先にページごとの要点と説明順を決め、`build(context)` から `Deck` を返すコードを書く。
ページ、図形、文章、線、矢印には、編集後も意味が変わらない識別子を付ける。繰り返す要素の識別子は番号でなく項目のキーから `key_id()` で作る。
文中の変数と数式は `Math` で指定し、本文とノートで記号の意味をそろえる。
参照する元資料と文献を `sources` に結び付ける。

領域を広げる、文章を整理する、図を分ける、ページを分ける、の順に読みやすさを検討する。
文字サイズを変更する場合は意図して指定し、選んだ役割の最小値を守る。
通常の本文を小さくするために、注記用の役割を流用しない。使う場所を限った役割は、使うページか要素の `allow_roles` で宣言する。

長い文は自動折り返しに任せ、意味の区切りで行を分けたい箇所だけ `\n` を入れる。1 行で収めたい見出しやラベルは `word_wrap=False` にする。
和文の段落で文節の途中の折り返しを避けるときは、`\n` を手で入れる代わりに書式 `phrase_wrap=True` を使う。収まるかは `slidekit measure` か `slide.measure()` で、生成せずに確かめる。
行数が変わる要素の高さは、座標を手で計算する前に、`Rect(x, y, w, None)`・`slide.stack()`・`slide.measure()` で内容から決める。

図のまとまりは `group` で作る。数式を含まないまとまりは PowerPoint のグループとして書き出される。
線は `anchor()` で図形に結ぶと、PowerPoint で図形を動かしても追従する。数式を含む図は回転・反転しない。
補足を指し示すときは、図形の書式 `tail_side` で吹き出しにするか、`tail_toward` に指す相手の `anchor()` を渡す（[吹き出し](../docs/usage.md#吹き出し)）。
画像やグラフの準備は資料側で済ませ、入力画像の文字と凡例も、読むのに十分な大きさにする。

## 生成し、機械検査する

```sh
slidekit layout --project src/deck.toml
slidekit build --draft --project src/deck.toml
slidekit build --project src/deck.toml
```

`layout` は表示ソフトを使わず、配置と記述規則の誤りを数秒で示す。編集のたびに使い、エラーがなくなってから生成する。
折り返しの位置（文節の途中、ハイフンの後、短い最後の行）は参考の診断と `layout --wraps` の行の文字列で先に確かめ、画像を開く回数を減らす。
合否は要約の最後の行（「結果: …」）と終了コードで判断する。
`build --draft` は互換画像を省いた下書きで、見た目を確かめるときに使う。直しているページだけを見るなら `--slides` を付ける。
下書きと部分生成は確認と完成物の対象外なので、完成させるときは通常の `build` で全ページを生成する。
`slidekit doctor` は、初回と、フォント・PowerPoint・`environment.toml` を変えたときに使う。`build` は同じ事前確認を内部で行うので、毎回 `doctor` を前に実行しなくてよい。

要約の診断を確認する。診断の意味と直し方は [診断の一覧](../docs/diagnostics.md) を参照する。
エラーは編集元を直して再生成する。警告も原因を確かめて修正し、意図した状態だけを、資料コードの `slide.allow_warning()` か `review accept` で理由付きで許容する。
生成後の PPTX や JSON を直接直して、生成記録と食い違わせない。

最初に生成した後の修正は原則 3 回までとし、依頼に別の指定があればそれを優先する。
修正の回数は作業者が把握する。上限に達して問題が残る場合は、未完成であることと未解決事項を報告する。

## 表示と内容を確認する

```sh
slidekit review status --project src/deck.toml
```

`build` は前の実行から、証拠が一致する確認を自動で引き継ぐ。`review status` が示す残りの確認を、画像と本文を開いて行う。
表示確認は最終 PPTX と同じスライドの XML を変換した画像（実行ディレクトリの `renders/` の画像）で行う。下書きや部分生成の画像を、完成したファイルの表示確認の代わりにしない。

一覧画像でページ順と全体の配置を確認し、文書情報と依頼内容との対応も確かめる。その後に、確認が残る全ページの個別画像を開く。
`build` の要約の前の実行との比較と、`review sheet` の比較画像（前の実行・標準表示・互換表示を並べ、差のある領域を枠で示す）は、見る場所を絞る助けにする。比較画像を見たことを、個別のページ画像の確認の代わりにしない。
文字の欠け、はみ出し、意図しない重なり、数式の記号、線の接続、表の行列、画像内の文字を確認する。配置だけを変えたページも、図の意味が変わっていないかを確かめる。
互換画像を付けた場合は、数式のページの互換表示の画像も確認する。

本文、図表、数式、ノート、出典、文書情報を元資料と依頼内容に照合する。
ノートの文体と論理の正しさは機械検査だけで判断しない。
画像を開けない場合は表示確認を完了として記録せず、確認できる人へ引き継ぐ。

実際に確認した範囲だけを `review record` で記録し、確認者と確認した内容を残す。`review status` が示すコマンドの置き場所（`<確認者>`・`<確認した内容>`）は、確認した後に書き換える。
未確認をすべて確かめたときは `review record --pending --status-id …` で 1 回で記録できる。種類ごとに確かめた内容が違えば `--note-visual` などで分けて書く。
`review.json` は手で編集しない。具体的なコマンドは [利用ガイド](../docs/usage.md#確認と完成物の保存) を参照する。

## 完成物へ反映する

```sh
slidekit export --project src/deck.toml --build latest
```

`export` は最終検査を行い、機械検査と確認記録の条件がそろった実行だけを反映する。
最終検査は実際に画像を見たか、主張が正しいかを自動で証明するものではない。
`export` に成功したら、固定パスの PPTX、PDF、ノートと、確認した範囲を利用者へ示す。
未確認の資料を確認済みの完成物として案内しない。

## 複数人で並行して書く

複数の作業者が章ごとに同時に書くときは、次のようにする。

1. 章ごとにモジュールを分け、生成関数では選ばれたページを含む章だけを読み込んで作る。読み込みも `if` の中で行えば、ほかの章の書きかけの誤り（構文の誤りを含む）で止まらない。

   ```python
   import importlib

   from slidekit import Deck

   CHAPTERS = {"chapters.intro": ("intro", "goal"), "chapters.method": ("method", "steps", "cost")}


   def build(context):
       deck = Deck(context)
       for module, slide_ids in CHAPTERS.items():
           if context.selected(*slide_ids):
               importlib.import_module(module).build(deck)
       return deck
   ```

2. 自分の章は `slidekit layout --project src/deck.toml --slides method,steps,cost` のように、ページの識別子で指定して検査する。
   番号や範囲を含む指定では、`context.selected()` が常に真になり全ページを構築するので、書きかけの章の誤りで止まる。
3. 選んだ章だけを構築した検査と生成では、ページを番号でなく識別子で示す。診断は `slide_number` を持たず、予測（`layout.json`）・生成記録・`deck.json` のページ番号は `None` になる。
   `notes.md` の見出し（「## 識別子. 題名」）とページ画像の名前（`slide-識別子.png`）も識別子になる。ページ番号の飾りだけは作ったページの中の番号である。
   ページ画像の名前では識別子のうち Windows のファイル名で禁止されている文字（`<`・`>`・`:`・`"`・`\`・`|`・`?`・`*`）と `%` を `%XX`（文字の番号の 16 進）にする（例：`a:b` は `slide-a%3Ab.png`）。
4. `layout` は表示ソフトを使わずファイルも書かないので、何人でも同時に動かすことができる。
5. `build` は PowerPoint の排他を待つ順番待ちになる。待つ間は標準エラーに「変換待ち: 別の処理が PowerPoint を使用中（実行 …、PID …、経過 N 秒）」が出る。待つ上限は `--wait` で決める。
6. 章のモジュールに構文の誤りがあると、失敗の診断の場所は、読み込んだ行でなく誤りのあるファイルと行になる。
7. `build --slides` と `--draft` の実行は完成物にできないので、最後に全ページを通常の `build` で生成してから確認する。
